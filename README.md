# Scooter Auth Tester

Тестовое Android-приложение: сканирует BLE-устройства, подключается, показывает
все GATT-сервисы и характеристики, подписывается на уведомления и умеет
вычислять/отправлять ответный хэш по алгоритму из `KugooCrypto.kt`
(порт присланного Python-кода, проверен — даёт тот же результат).

**Это инструмент диагностики, а не готовый клиент самоката.** Точные UUID
сервиса/характеристики твоей конкретной модели неизвестны, поэтому
приложение показывает вообще всё, что отдаёт устройство по BLE, и даёт
самому увидеть, через какую характеристику приходит "+PM>..." и куда писать ответ.

## Протокол (из декомпиляции LFBluetootService.java + BleMutualAuthentication.java)

Полное взаимное рукопожатие выглядит так:

1. Приложение → `+VER?`
2. Самокат → `+VER=<версия>`
3. Приложение → `+PM?`
4. Самокат → `+PM><nonce, 12 hex>`
5. Приложение считает хэш алгоритмом из `KugooCrypto.kt` → `+PM<<hash, 8 hex>`
6. Самокат → `+PM=OK` (хэш верный) или `+PM=NK` (неверный — пробуй другой mode)
7. Если OK: приложение генерирует случайный код (6 случайных байт 0-255 как
   десятичные цифры подряд, не hex) → `+PA<<code>>`, сам у себя заранее
   считает ожидаемый хэш от этого кода
8. Самокат шифрует тот же код своим ключом и шлёт `+PA><hash, 8 hex>`
9. Приложение сверяет хэш — если совпало, авторизация пройдена полностью

`mode` (1/2/3) — это тот же `CONNECT_TYPE`, что определяется по тому, какая из
трёх пар UUID сервиса/характеристики (см. `KNOWN_SERVICES` в `MainActivity.kt`)
реально есть у самоката.

## Как пользоваться

1. Собери APK (см. ниже) и установи на телефон.
2. Включи Bluetooth и геолокацию (на Android < 12 это нужно для BLE-скана).
3. Нажми «Сканировать», выбери самокат в списке.
4. После подключения в логе появится список сервисов/характеристик. Если
   среди них нашёлся один из известных (`KNOWN_SERVICES`), приложение
   покажет это в статусе и выставит правильный `mode` само.
5. Если галка «Авто-рукопожатие +VER/+PM/+PA» включена (по умолчанию да) —
   примерно через 0.5 сек после обнаружения сервисов приложение само
   запускает весь протокол и ведёт его до конца, печатая каждый шаг в лог.
6. Если самокат не ответил или сессию нужно начать заново — жми кнопку
   «Запустить рукопожатие заново (+VER?)».
7. Если на шаге 6 протокола пришло `+PM=NK` — mode не подошёл, переключи
   радио-кнопку mode вручную (это имеет смысл, только если самокат не был
   распознан автоматически по UUID) и нажми рукопожатие заново.
8. Строка в логе `ВЗАИМНАЯ АВТОРИЗАЦИЯ ПРОЙДЕНА` = полный успех.

Отдельно есть кнопка **CODE=** — это независимый PIN-код механизм из
оригинального приложения (`sendString("CODE=" + password)`), не связанный
с +PM/+PA напрямую; используй, если самокат явно просит код/пароль.

## Исправлена подписка на уведомления (notify) — вероятная причина "самокат вообще не отвечает"

Раньше при обнаружении сервисов приложение для каждой характеристики с
notify/indicate сразу вызывало `writeDescriptor()` в цикле, без очереди.
Android же разрешает только одну GATT-операцию "в полёте" на всё
соединение сразу — если у самоката больше одной такой характеристики
(а обычно есть ещё системные, не относящиеся к протоколу), включалась
только первая, остальные — молча нет. Если "молча нет" досталось именно
нужной характеристике — вот и объяснение, почему лог не показывал вообще
ни одной входящей строки, хотя команды (запись) исправно доходили до
самоката.

Теперь и запись характеристик, и запись дескрипторов (notify) идут через
одну общую очередь, а в лог добавлена отдельная строка про каждый
дескриптор: `Descriptor ... -> status=0 (notify включён)` или
`... (ОШИБКА — notify НЕ включён на этой характеристике!)`. Если увидишь
"ОШИБКА" рядом с characteristic `...bdc4...` (это как раз read/notify-
характеристика из уже распознанного протокола) — значит, дело было
действительно в этом.

## Приборная панель и исправление "Опросить статус"

Теперь два переключателя сверху: **Диагностика** (всё, что было) и
**Приборная панель** (крупно скорость/батарея/остаток хода + три выпадающих
списка, где вручную указываешь, какое из полей "Телеметрия" чем является —
мы не можем угадать это заранее для твоей конкретной модели, зато список
обновляется сам по мере появления новых полей).

Кнопка **"Опросить статус"** не работала из-за реального бага Android BLE:
`BluetoothGatt` разрешает только одну запись "в полёте" одновременно — если
вызвать `writeCharacteristic()` второй раз до того, как пришёл ответ на
первую, система тихо отклоняет вторую запись (без ошибки, просто ничего не
уходит на самокат). Кнопка слала 7 команд почти одновременно — большинство
терялось. Теперь все записи (включая блокировку/круиз/свет/передачи/CODE=)
идут через внутреннюю очередь и ждут подтверждения предыдущей, прежде чем
слать следующую.

## Как работает блокировка самоката и экран ввода кода

В протоколе два независимых механизма:

1. **"Мягкая" блокировка `+LOCK=1` / `+LOCK=0`** — электронно блокирует/
   разблокирует газ. Работает только после того, как пройдена основная
   авторизация (`ВЗАИМНАЯ АВТОРИЗАЦИЯ ПРОЙДЕНА`). Кнопки
   "Заблокировать"/"Разблокировать" в приложении уже это делают.
2. **Пароль/PIN через `CODE=<код>`** — отдельный канал, в ответ приходит
   `CODE_OK` или `CODE_NG`. Похоже, именно на него завязан экранчик самоката:
   когда он показывает режим ввода кода, он ждёт, что по Bluetooth придёт
   правильный `CODE=...` с телефона — набор цифр на самом самокате без
   участия приложения может не подтверждаться именно потому, что
   подтверждение (условно "рукопожатие согласия") идёт по BLE, а не локально.

Что стоит попробовать:

1. Подключись в приложении, дождись `ВЗАИМНАЯ АВТОРИЗАЦИЯ ПРОЙДЕНА`.
2. Введи пароль в поле ручной отправки и нажми **CODE=**. Если пароль
   раньше задавался/запоминался через оригинальное приложение Kugoo Kirin —
   используй тот же. Частые дефолтные варианты у таких клонов: `0000`,
   `000000`, `123456` — но гарантии нет, это нужно пробовать.
3. Если `CODE_NG` — пароль неверный, пробуй другой.
4. Если вообще никакого ответа (ни OK, ни NG) — раньше в этом мог быть
   виноват тот самый баг с GATT-очередью (см. выше), теперь это исправлено,
   попробуй ещё раз.

Если ни один из вариантов не подтверждается, не исключено, что у конкретно
твоей модели PIN на экранчике — чисто локальная функция (без какого-либо
участия Bluetooth вообще, сверяется прошивкой самой платы), тогда дело не
в приложении, а в последовательности физических нажатий кнопок на самом
самокате — для этого нужна инструкция именно твоей модели.

## Телеметрия и команды управления

После успешной авторизации появляется блок с кнопками и живой панелью
"Телеметрия". Команды — это реальные строки/hex-кадры протокола из
декомпиляции `VehicleFragment.java` оригинального приложения Kugoo Kirin:

- **Блокировка/разблокировка**: `+LOCK=1` / `+LOCK=0`
- **Круиз-контроль**: `+CRZE=1` / `+CRZE=0`
- **Передачи**: `+MODE=<1..5>` (текстовый протокол) — кнопки сами считают
  текущую передачу и шлют +1/-1. У части моделей (`kgkrn03/04/05`) передачи
  переключаются не текстом, а hex-кадрами из заранее заданного списка —
  если `+MODE=` не действует, напиши, какая у тебя модель, добавим hex-ветку.
- **Свет**: по умолчанию текстом `HLGT=1`/`HLGT=0`. Часть моделей
  (`kgkrn02`, `b1/b2/b11/b17/b205`, `kug03/11/19/20` и т.п.) управляют светом
  бинарными кадрами `AA070601AABB` (вкл) / `AA070600ABBB` (выкл) — включи
  галку "Бинарный протокол света", если текстовая команда не сработала.
- **Опросить статус (?)** шлёт серию запросов `+MODE=?`, `+LOCK=?`, `+UNIT=?`,
  `+CRZE=?`, `+SPDLT=?`, `HLGT=?`, `+MDMX=?` — самокат должен ответить тем же
  ключом с текущим значением.

Панель "Телеметрия" разбирает **любую** входящую строку вида
`+КЛЮЧ=значение` (включая `HLGT=` без `+`) и показывает её живьём. Известные
поля подписаны по-русски, а всё незнакомое показывается как есть с пометкой
"похоже на скорость/батарею/..." — так его проще заметить в потоке.

**Важно про скорость/батарею/пробег/температуру/ошибки**: в оригинальном
приложении код, который их разбирает, лежит в одном огромном
`BroadcastReceiver.onReceive()` — и именно этот метод не восстановился при
декомпиляции (JADX дал "Method not decompiled", инструкций слишком много).
Известно только, что `showSpeedView(float)` ждёт "сырое" значение/10 (км/ч),
`showBatteryView(int)` — готовый процент, `showMileageView(int type, float)` —
тоже значение/10 (км), а самопроверка (`CheckInfoActivity`) шлёт отдельные
биты неисправностей по разным "железным" пунктам (тормоз, холл-датчик,
контроллер, температура батареи/мотора и т.п.) — тоже в недекомпилированном
виде и по-разному для каждой модели.

Поэтому точный формат (текстом `+КЛЮЧ=значение` или бинарным кадром
`AA ... BB`) для ИМЕННО твоего самоката нужно подсмотреть вживую:

1. Подключись, дождись `ВЗАИМНАЯ АВТОРИЗАЦИЯ ПРОЙДЕНА`.
2. Поезди/покатай колесо рукой, последи, как меняется число в приложении
   (или на дисплее самоката) — скорость.
3. Параллельно смотри лог — если самокат использует текстовый протокол,
   в "Телеметрия" появится новое поле само (например `WS=123` или подобное).
   Если ничего не появляется — у него бинарный протокол, тогда сравнивай
   hex-кадры в логе "до" и "после" изменения скорости/заряда: тот байт,
   который меняется синхронно со спидометром — это и есть скорость (как
   правило raw-значение нужно поделить на 10, по аналогии с showSpeedView).
   То же самое для заряда (меняй его искусственно сложно, но обычно это
   отдельный байт 0..100), пробега и температуры.
4. Когда нашёл нужный байт/поле — напиши мне его позицию и значения в
   нескольких ситуациях, я добавлю разбор именно этого кадра в приложение.

   `.github/workflows/build-apk.yml`):

   cd scooter-app
   git init
   git add .
   git commit -m "Scooter auth tester"
   git branch -M main
   git remote add origin https://github.com/<твой_логин>/<репозиторий>.git
